# muzzle v1: did it help?

Status: closed 2026-11-06. §1 baseline (to 2026-10-29); §2 tier-2 replays
on muzzle 0.2.4 (light load, a high-load ladder, a budget sweep); §3 the
rollout week was not run; §4 verdict. Results: `docs/bench/0.2.4/`.

## 1. Baseline (before muzzle)

**Source:** museum, linuxpc sessions only (D37), from 2026-10-17 (the first
day museum records measured tool durations, D43) to 2026-10-29. Every bash
call is labelled with the reviewed rule config `bench/linuxpc-config.toml`
(hash b7e2bb) via `muzzle match`, so the labels match the traces and the
rollout. Only **measured, foreground** calls count toward durations (D42).
Background launches are counted, but their durations are not used.

**Method** (rerun to reproduce; the second command needs the labelling step):

```sh
S=museum/skills/museum/scripts/museum-search
"$S" calls swayward --since 2026-10-17 --until 2026-10-29 --tool bash --limit 1000000 --json > swayward.json
"$S" calls mu       --since 2026-10-17 --until 2026-10-29 --tool bash --limit 1000000 --json > mu.json
# keep linuxpc/ files, dedupe on (file, start, command[:200]), label each command with:
XDG_CONFIG_HOME=<dir holding bench/linuxpc-config.toml as muzzle/config.toml> muzzle match --json -- '<command>'
```

**Coverage:** 37,990 unique linuxpc bash calls from the `swayward` and `mu`
project queries (all linuxpc bash calls in the window: 44,195); 2,250 match a rule. Measured
foreground share per rule: js-test 99%, cargo-test 90%, gate 95%, fast-gate
100%, oracle-sweep 100%.

### Throughput

From mu's own task DB (it keeps workstreams from 10-28; museum's 300-char
commands can't count task ids, see the fact-check). A unit is a `work` task
closed `done`, excluding review and finding tasks; an **active hour** is a
UTC hour with at least one such close.

```sh
mu sql "SELECT substr(t.updated_at,1,13) AS hr, count(*) AS n FROM tasks t
  WHERE t.status='CLOSED' AND t.substate='done' AND t.kind='work'
    AND t.local_id NOT LIKE 'review%' AND t.local_id NOT LIKE 'rv%'
    AND t.updated_at>='<START>' AND t.updated_at<'<END>' GROUP BY 1"
```

| day | done units | active hours | per active hour |
| --- | ---: | ---: | ---: |
| 2026-10-29 | 85 | 13 | 6.5 |
| 2026-10-30 | 71 | 13 | 5.5 |

Both days already ran muzzle for this crew's own gates (dogfood) and for
every pi session with the extension, so they are a **pre-rollout** figure,
not a muzzle-free one. The rollout week uses the same query; the criterion
"merged per hour not lower" compares per-active-hour rates, and a shift under
15% is noise (different work, different crews).

### What this baseline can't say

- The overload days (10-05 to 10-10) are outside it: museum had only
  estimated durations then (D43), and the replay uses them as workload only.
- 10-29 already includes muzzle's own dogfood runs (this crew's gates ran
  through muzzle from 13:51Z). It stays in the baseline as a known mix. No
  rollout followed (§3), so the window was not refreshed.
- Gate time depends on the code being tested, which changes over the window
  (dogfood_report lesson 1). Before/after comparisons use the same rules over
  comparable weeks, and treat p90 shifts under 15% as noise.

## 2. Replay (tier 2, none vs muzzle)

All runs: linuxpc (16 cores, 31 GB), muzzle 0.2.4, live config hash 5f9103
(budget 14 = 16 cores − reserve 2), no mu agents running. The commands are
the real swayward and swaywardlock gates through `distrobox enter
swayward-dev`, so muzzle admits them but enforces no caps or scope (D16a),
and the figures cover time, slots, load and the probe, not per-job CPU or
memory. `--mode none` is today's practice (C3): every call starts at once
with the role caps (`CARGO_BUILD_JOBS` 4 for workers, 6 for the orchestrator,
2 otherwise). Each agent has its own worktree, built once before the run.
Results: [`docs/bench/0.2.4/`](../bench/0.2.4/). The kit (`real-*.toml`,
the runner scripts) is local to linuxpc; it names paths.

Figures for matched calls leave out `unmatched-heavy` calls, which never
queue. Wait counts from call start to admission; run counts from admission
to end.

### 2a. The busiest real windows at real speed: no measurable cost

Each trace's busiest 3 h window replayed at speed 1, calls run against warm
worktrees (`2026-10-21-*`, `2026-10-08-*`).

| trace | mode | calls (failed) | makespan | wait p90 | run p50/p90 | slots max | load1 p50/max | git status p95 | sleep late p99 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10-21 | none | 79 (0) | 10979 s | 0.0 s | 4.0/98.2 s | 12 | 0.33/4.3 | 3.36 ms | 0.49 ms |
| 10-21 | muzzle | 79 (0) | 10979 s | 0.01 s | 5.1/97.0 s | 12 | 0.30/3.6 | 3.35 ms | 0.49 ms |
| 10-08 | none | 121 (0) | 10891 s | 0.0 s | 34.3/80.3 s | 12 | 2.99/7.9 | 3.36 ms | 0.46 ms |
| 10-08 | muzzle | 121 (0) | 10891 s | 0.02 s | 35.1/79.8 s | 12 | 2.96/7.7 | 3.38 ms | 0.45 ms |

The two modes match within the noise. Neither window reached the 14-slot
budget, so muzzle almost never queued: the longest wait was 41 s, for one
`fast-gate` call (from the run's per-call reports, kept locally; the result
files carry only percentiles). **This proves no harm at low and moderate load, and
nothing about overload.** Warm worktrees at one commit make the calls
cheaper than on the recorded day, so these windows load the machine less
than the real days did.

Two notes on reading these files. The all-calls run p50 in the 10-21 files
(38.0 s vs 5.2 s) is a cliff: run times split into ~4 s cargo tests and
≥30 s unmatched burns, and call 39 of 79 sits on the edge. Use the matched
figures. The first 10-08 attempt was invalid, with 62 of 121 calls failed:
the fresh worktrees lacked swayward's untracked i3 oracle. It was rerun
after `setup` ran `contrib/fetch-oracle`.

### 2b. High load: the 10-08 window compressed 6×, 12× and 24×

To reach overload, the 10-08 window is replayed at `--speed` 6, 12 and 24.
Calls arrive 6 to 24 times as densely, while each real command takes as
long as it takes. Every call first touches `src/lib.rs`, so it recompiles
the crate as it would after an agent's edit (`2026-10-08-x<speed>-*`).

| speed | mode | jobs/h | wait p90 | run p50/p90 | slots max | load1 p50/max | git status p95 | sleep late p99 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 6× | none | 238 | 0 s | 58/146 s | 40 | 9.2/29 | 7.8 ms | 1.02 ms |
| 6× | muzzle | 201 | 239 s | 52/94 s | 12 | 7.8/15 | 5.9 ms | 0.72 ms |
| 12× | none | 408 | 0 s | 111/329 s | 76 | 22.6/90 | 31.3 ms | 2.87 ms |
| 12× | muzzle | 247 | 619 s | 57/99 s | 12 | 9.7/20 | 7.0 ms | 0.95 ms |
| 24× | none | 486 | 0 s | 324/561 s | 160 | 68/157 | 102.9 ms | 3.20 ms |
| 24× | muzzle | 248 | 1066 s | 63/96 s | 12 | 9.3/19 | 6.6 ms | 0.92 ms |

OOM kills: 0 in every run.

- **muzzle holds the machine.** Load stays at or under 20, git status p95
  at about 7 ms or less (5.9 to 7.0), and run p90 flat at ~95 s at every speed. Without it, load
  reaches 157 on 16 cores, git status p95 15 times slower (103 ms), and each
  job takes up to 6 times longer (run p90 561 s).
- **At the default budget muzzle costs throughput.** It plateaus at
  ~248 jobs/h, 40% below none at 12× and 49% below at 24×, while load1 p50
  stays around 9 on 16 cores. Wait plus run per job comes out worse than
  none's run alone. The slots are claims of peak parallelism, and these
  gates spend much of their time below the peak (fmt, link, doc checks and
  Python checks run on one core). `fast-gate` claims 6 and `cargo-test` 3,
  so a few claims fill the 14 slots while cores sit idle.

### 2c. Budget sweep at 12×

The same 12× muzzle run with an explicit budget (`slots = N`, config copies
under `XDG_CONFIG_HOME`; the live config unchanged)
(`2026-10-08-x12-muzzle-budget<N>`).

| budget | jobs/h | wait p50/p90 | run p50/p90 | slots max | load1 p50/max | git status p95 | sleep late p99 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| none (role caps) | 408 | 0/0 s | 111/329 s | 76 | 22.6/90 | 31.3 ms | 2.87 ms |
| 14 (default) | 247 | 144/619 s | 57/99 s | 12 | 9.7/20 | 7.0 ms | 0.95 ms |
| 20 | 316 | 65/343 s | 72/113 s | 18 | 14.2/24 | 8.4 ms | 1.44 ms |
| **24** | **353** | 2/195 s | 74/132 s | 24 | 16.4/25 | 9.7 ms | 1.87 ms |
| 32 | 365 | 15/183 s | 107/142 s | 30 | 21.6/37 | 12.2 ms | 2.39 ms |

A budget of 24 (1.5× cores) recovers most of the throughput: 13% below none
instead of 40%. It keeps load1 max at about 25 (25.4) and git status p95 under 10 ms,
and its wait p90 plus run p90 (~327 s) is close to none's run p90 (329 s).
Going to 32 adds 3% throughput at a clear cost in responsiveness.

### Limits of 2b and 2c

- **Failed calls (3 to 11 per run, both modes) are a bench artifact.**
  Compressing time makes one agent's consecutive calls overlap in its single
  worktree, which never happened on the real day. In the 6× muzzle run, all 3
  failures were `cargo-test` calls overlapping another call by the same agent
  in its worktree (25 such pairs in that run, counted from its local per-call
  reports against the trace). So these runs can't measure load flakes. A
  fix is to serialise each agent's calls in `bench run`.
- One workload (swayward gates), one machine, gates in a container (no
  enforced caps), one speed for the sweep.
- `none` is the hand-capped practice of late October. The uncapped practice
  of the overload days (every cargo at all cores) wasn't run, and would be
  worse than `none`.

## 4. Verdict

Against the success criteria (spec §Goal), with the evidence there is:

| criterion | evidence | result |
| --- | --- | --- |
| gate p90 under ~150 s at 16 agents | The result files give run p90 over all matched calls (gates, cargo test, js test), not the gate rule alone, and warm worktrees make §2a's calls cheaper than the recorded day, so §1's gate p90 (368 s) and §2a's (<100 s) don't compare. §2b: under overload, matched run p90 stays at 94–99 s under muzzle while none's grows to 561 s; with the queue included, neither mode stays under 150 s at 12× and above | **not measured** for gates; it needed the rollout week. Under overload muzzle keeps the run time steady, not the end-to-end time |
| no load-induced flakes | §2a: 0 failures in all four runs. §2b: no OOM kills; the failures are the overlap artifact | none seen in the speed-1 replays; not tested under overload |
| merged per hour not lower | At speed 1 the trace fixes arrivals, so §2a's equal jobs/h only shows muzzle didn't stretch the tail (makespan equal). §2b: 40–49% fewer jobs/h at the default budget, 13% fewer at budget 24 (§2c). Merged tasks per hour is a rollout-week figure (D44 point 2) | **not measured** in real use; **lower under overload at the default budget** |

Extra, from the probe (D44 point 3, not a §Goal criterion):

| figure | evidence | result |
| --- | --- | --- |
| responsive machine | §2a: probe identical. §2b: git status p95 5.9–7.0 ms under muzzle at every speed, against 7.8, 31 and 103 ms without | **held under muzzle**, the clearest result |

**In one line:** in these replays muzzle costs nothing when the machine isn't
contended, and under overload it keeps the machine responsive and each job's
run time steady. At the default budget it pays for that with throughput, and
a larger budget buys most of the throughput back. The §Goal criteria on gate
p90 and merged per hour need the rollout week, which didn't run.

**Recommendations**

1. **Machines whose gates claim more than they use** (container gates, or
   gates with long single-core stretches) should set an explicit budget of
   about 1.5× cores. On linuxpc that is `slots = 24` in `machine.toml`.
   Container gates have no CPU figures (D16a), so judge by the queue and the
   machine: frequent waits while load stays well under the core count mean
   the budget is too small, and a slower probe (`muzzle bench probe`) means
   it is too big. Where CPU is measured, `muzzle report`'s high utilisation
   with low CPU efficiency says the same (`recipes/tune.md`).
2. **Keep the default (cores − reserve, D7) for now.** This is one workload.
   Before changing D7, check whether the lost throughput comes from one
   over-sized weight (`fast-gate` at 6) rather than the budget rule: rerun
   §2c with budget 14 and `fast-gate` at 3. If it does, the fix is the
   weight. If not, add an overcommit factor to D7 and say how D9's memory
   caps scale with it.
3. **Fix the bench before the next high-load run**: serialise each agent's
   calls under `--speed`, so failures measure flakes.

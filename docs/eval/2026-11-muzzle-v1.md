Status: section 1 (baseline) first cut, 2026-10-29. Sections 2-4 follow the

## 1. Baseline (before muzzle)

**Source:** museum, linuxpc sessions only (D37), from 2026-10-17 (the first
day museum records measured tool durations, D43) to 2026-10-29. Every bash
call is labelled with the reviewed rule config `bench/linuxpc-config.toml`
(hash b7e2bb) via `muzzle match`, so the labels match the traces and the
rollout. Only **measured, foreground** calls count toward durations (D42).
Background launches are counted, but their durations are not used.

**Method** (rerun to reproduce; the second command needs the labelling step):

```sh
S=museum/skills/museum/scripts/museum-search
"$S" calls swayward --since 2026-10-17 --until 2026-10-29 --tool bash --limit 1000000 --json > swayward.json
"$S" calls mu       --since 2026-10-17 --until 2026-10-29 --tool bash --limit 1000000 --json > mu.json
# keep linuxpc/ files, dedupe on (file, start, command), label each command with:
XDG_CONFIG_HOME=<dir holding bench/linuxpc-config.toml as muzzle/config.toml> muzzle match --json -- '<command>'
```

**Coverage:** 37,990 unique linuxpc bash calls; 2,250 match a rule. Measured
foreground share per rule: js-test 99%, cargo-test 90%, gate 95%, fast-gate
100%, oracle-sweep 100%.

### What this baseline can't say

- The overload days (10-05 to 10-10) are outside it: museum had only
  estimated durations then (D43), and the replay uses them as workload only.
- 10-29 already includes muzzle's own dogfood runs (this crew's gates ran
  through muzzle from 13:51Z). It stays in the baseline as a known mix; the
  refresh before rollout ends the window at the rollout start.
- Gate time depends on the code being tested, which changes over the window
  (dogfood_report lesson 1). Before/after comparisons use the same rules over
  comparable weeks, and treat p90 shifts under 15% as noise.

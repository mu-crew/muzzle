# muzzle 0.2.3: slow holders and waiters in `status`, and a tmux pill

Status: approved by the human (2026-10-31, Q1–Q5 "agreed"). It adds fields to
the v1 spec's §Interface `status --json`, which stays add-only (AGENTS.md
invariants). This spec wins where they disagree.

## Problem

The mu-crew tmux status line shows agent counts, CPU and memory, but nothing
says why a host feels slow. When builds are being held back, the slots are the
reason, and today the only way to see them is to run `muzzle status`. Two
things are worth showing: a job that runs much longer than its usual time (it
may be hung, or the host may be overloaded), and a job that has been queued a
long time (too few slots).

This host's `runs.jsonl` on 2026-10-31 (2192 runs) shows why one fixed
threshold won't do:

| rule | runs | p50 | p90 | max |
| --- | --- | --- | --- | --- |
| cargo-test | 1523 | 4.6 s | 81 s | 1143 s |
| vtmux-harness | 232 | 9.7 s | 70 s | 417 s |
| vtmux-check | 126 | 108 s | 240 s | 327 s |
| js-test | 89 | 2.0 s | 51 s | 495 s |

Waits: p50 4 ms, p99 25 s, max 70 s.

## Decisions

**S1 The slow rules live in muzzle, in `status --json`** (Q1). No new
subcommand or text format. The poller reads the JSON as it reads
`murmur status --json`. Why: `status --json` is already the contract mu host
integration reads, and it is add-only. A second format would be a second
contract. Typical run times need `runs.jsonl`, which only muzzle should parse.

**S2 Slow holder** (Q2). A holder is slow when all of these hold:

- there are at least 10 earlier runs with the same `(repo, rule)`, `exit == 0`
  and `killed == null`, counted from the most recent 50 such runs in the live
  `runs.jsonl`;
- `run_s > typical_s`, where `typical_s` is the p90 of `ran_s` over those
  runs (nearest-rank, rounded up to whole seconds);
- `run_s >= 60`.

A holder whose `rule` or `repo` is null gets null for `typical_s` and is never
slow. Why: one rule name means different things in different repos. Ten runs
keep a new rule from being flagged on its first run. The 60 s floor stops
short jobs that ran a little long from lighting up the pill. Only successful,
unkilled runs count, so a timed-out run doesn't push p90 up.

**S3 Slow waiter** (Q3). A waiter is slow when `age_s >= 30`. Why: 30 s is
when `muzzle run` prints its first queued line (D13), and it is just above the
observed p99 wait. A wait depends on the queue, not the rule, so history adds
nothing.

**S4 Fields, added only.**

- Each holder: `typical_s` (integer or null) and `slow` (bool).
- Each waiter: `slow` (bool).
- Top level: `slow_holders` and `slow_waiters` (integers).

Text `status` shows `slow` after `run_s`, as `120s (slow, usually ≤45s)`, and
marks slow waiters with `(slow)`. It adds nothing when nothing is slow.

**S5 Read cost** (Q5). Read only the live `runs.jsonl`, never the gzipped
archives, and only when there is at least one holder with a non-null `rule`
and `repo`. Read the file once per `status` call and build a map from
`(repo, rule)` to its typical time for just the holders' keys. Lines that fail
to parse are skipped. A missing file means no history. Why: the pill polls
every 5 s. The live file is about 900 KB here, and 50 recent runs per key
nearly always fit in it. After a rotation, a key may have too little history
for a while and shows `typical_s: null`, which is safe.

**S6 The `status` S2 window is computed outside `view`.** `view` stays free
of I/O (it is unit-tested with a liveness table). `main` reads the typical
times and passes them in as `&HashMap<(String, String), u64>`. `slow` is
decided inside `view` from `run_s`, `typical_s` and the 60 s floor, and from
`age_s` for waiters.

## The tmux side (dotfiles, separate commit)

**T1 A `muzzle` probe** in `tmux/scripts/mu-crew-poller`, on a 5 s interval,
opt-in through `@mu_crew_probes` like the others. It runs
`muzzle status --json` and writes:

- `@mu_crew_muzzle_held`, `@mu_crew_muzzle_budget`: always set while muzzle
  answers
- `@mu_crew_muzzle_waiting`, `@mu_crew_muzzle_slow_holders`,
  `@mu_crew_muzzle_slow_waiters`: unset at zero, as murmur does with its counts

On any failure (no `muzzle` on PATH, an exec error, a non-zero exit, bad
JSON) the probe clears its options and tries again next tick. Review panel
2026-10-31 (F1): stopping on a missing binary, as `murmur_remote` does,
latched the pill off for the loop's life after a moment's gap during an npm
reinstall.

**T2 `@mu_crew_muzzle_pill`** in `tmux/mu-crew.conf`, a plain format with no
process on redraw. It is empty unless held > 0 or waiting > 0. In order:

- a muzzle glyph, then `held/budget` in `@mu_crew_c_working`
- waiting count and glyph in `@mu_crew_c_waiting`
- slow holders count and glyph in `@mu_crew_c_blocked`
- slow waiters count and glyph in `@mu_crew_c_error`

Each count is hidden at zero. New glyph options `@mu_crew_g_muzzle`,
`@mu_crew_g_queued`, `@mu_crew_g_slow` and `@mu_crew_g_starved` go in the
`mu-crew-glyphs` THEME block, with ASCII fallbacks under `@mu_crew_ascii`.
The user places it in their own `status-right`, next to `@mu_crew_pill`.

## Builder's calls (builder check, 2026-10-31: nothing important left)

- "Most recent" is file order in `runs.jsonl`; appends are under the state
  lock. A holder's own run isn't in the file until it ends.
- `view` stays at its seven arguments (clippy's limit); a pure
  `Status::mark_slow(&Typical)` fills `typical_s`, `slow` and
  `slow_holders` after it. That is S6's shape with one more step.
- `@mu_crew_muzzle_waiting` counts waiters, not their slots.
- An older muzzle on PATH (no `slow_*` fields) reads as zero slow.
- Unlike `murmur_remote`, which publishes nothing when `murmur` is missing,
  the muzzle probe clears every option it owns and keeps polling.

## Out of scope

- Remote hosts' muzzle state (Q2 of the first round: local only).
- A per-rule wait threshold, or "usually takes ~Xm" in the queued line (still
  an `IDEAS.md` evaluate item; this gives it data, it doesn't ship it).
- Pushing tmux options from `muzzle run`. Polling stays: dead holders are only
  pruned when something reads the state, and muzzle stays unaware of tmux.
- Reading archives for typical times.

## Tests

- muzzle `status.rs` unit tests: slow and not-slow holders around p90 and the
  60 s floor, under 10 runs, null rule/repo, waiter at 29 s and 30 s, the top
  level counts, and the new fields present in `json_has_every_spec_field`.
- muzzle `runlog.rs` unit tests for the typical-time reader: only the last
  50 per key, only `exit == 0` and `killed == null`, bad lines skipped,
  missing file.
- dotfiles `tests/test_poller.py`: the probe's options from a fixed JSON,
  unset at zero, cleared when muzzle is missing or fails.
- dotfiles `tests/test.sh`: the pill expands to empty with nothing held, and
  shows each part in a tmux server with the options set.

# muzzle v1: per-host admission for heavy commands, with a run log that tunes itself

Status: approved design, not started.
Date: 2026-10-29

## Problem

A crew of agents on one machine runs gates, builds and test suites at the same
time. Each one sizes itself for the whole machine. Together they overload it:
gates get slower for everyone, the interactive side stutters, and timing tests
flake.

Evidence from museum (`museum-search stats`, linuxpc, 16 cores / 31 GB):

- Gate-like bash calls (`fast-gate`, `contrib/gate`, `cargo test|clippy`,
  `vitest`) in swayward/mu went from median ~15 s / p90 ~100–150 s in mid
  September to median 35–89 s / p90 600–830 s during the 5–10 October
  fan-out. Tool time was 100–170 h/day.
- Sessions logged load averages of 21, 25, 38 and 46. Fallout: a
  swaywardlock e2e "timing failure under load average ~25"; a mu perf audit
  whose timings were "noisy" at load 38–46; murmur dropping ~40% of `j`/`k`
  presses at load 21 (2026-10-07).
- The caps in use today are hand-written and kept in prose. Briefs set
  `CARGO_BUILD_JOBS=4` (workers), `6` (orchestrator) and `2` (reviewers), and
  say "never run two gates at once". `orch-gate.sh` caps the container at
  20 GB. swayward's `scratch/orch/small-run.sh` has four shared `flock` slots
  under `systemd-run --scope -p MemoryMax=4G`, plus an exclusive
  `oracle-sweep.lock`. tuicr (2026-10-26) cut from 16 agents to 8.
- Priority inversion, 2026-10-08: the orchestrator's merge check waited
  behind the workers' small-run slots and had to be given a reserved slot by
  hand (a linuxpc orchestrator session, 2026-10-08).
- mu's ROADMAP parks "Global delegate cap" as *needs evidence*. The evidence
  above answers its question: the resource that hurts is CPU and RAM per
  machine.

Nobody knows the right weights. Today's caps are guesses, and nothing
measures them. A static admission tool would only replace one set of guesses
with another. So v1 is two things:

1. **Admission.** A weighted slot budget per host, so the machine stays usable
   and the gates that unblock others go first.
2. **Measurement and tuning.** A run log of what every admitted job actually
   used, a report that suggests weights from that log, and a benchmark that
   replays real days. These make "did muzzle help" and "what should this gate
   weigh" questions with answers. *(user: "this takes the tool from maybe
   useful to very powerful; core v1.")*

## Goal and success criteria

Success (user-agreed, Q6):

- gate p90 back under ~150 s at 16 agents;
- no load-induced flakes;
- merged tasks per hour no lower than before.

These are claimed only through the evidence in [Proof](#proof-did-muzzle-help)
(D44): a replay of a real day, the rollout week compared against a museum
baseline, and an interactive probe. The eval reports what the numbers say,
slowdowns included. leasehold's benchmark found the same work taking up to
1.5× as long in return for a responsive machine, so the throughput criterion
needs watching.

## Decisions

Decisions marked *(user)* were agreed in the brainstorm. Ones marked *(my
call)* were filled in by the designer and are open to change. Numbers such as
Q33 refer to the brainstorm round in which a decision was made.

### Scope

- **D1 (user).** Gate heavy **commands**, not agents. An agent mostly waits on
  its model; the load comes from gates running together.
- **D2 (user).** Build per-host admission (A) first. Placement across hosts
  (B) is the next spec and only uses (A)'s `status` (see
  [Next](#next-mu-host-integration)).
- **D3 (user).** A new standalone tool, **muzzle**, in Rust, in its own
  `mu-crew/muzzle` repo. No daemon. mule stays "remote needs only tmux", and
  mu coordinates agents rather than owning a machine's CPU. A non-mu shell or
  another harness can use muzzle too.
- **D4 (user).** Build muzzle rather than adopt leasehold (see
  [Prior art](#prior-art)). Until v1 ships, GNU `sem` can stand in
  (`sem --id gate -j 2 …`).
- **D5 (user).** Supported on Linux and macOS.
- **D6 (user).** The run log, `report` with suggestions, the benchmark and
  the skill are core v1, not follow-ups.

### Capacity

- **D7 (user).** Budget = logical cores − reserve, one slot per core. Default
  reserve 2, overridable per host (`reserve =` or an explicit `slots =`).
  Linux: `available_parallelism`, which respects cgroup CPU limits. macOS:
  `hw.logicalcpu`. Apple E-cores count as full slots.
- **D8 (user).** A job claims N slots (default 1). A request larger than the
  budget is capped to the whole budget, so the job runs alone. This replaces
  exclusive locks such as `oracle-sweep.lock`.
- **D9 (user).** Memory comes from the same slots. A job's memory cap is
  `RAM / cores × N`, with no separate memory budget.

### Queue

- **D10 (user).** Two classes, `high` and `normal`. High waiters go ahead of
  every normal waiter but never pre-empt a running job.
- **D11 (user).** Strict first-come, first-served within a class. Nothing
  jumps ahead: when the head of the queue does not fit, everything behind it
  waits too. Without known run times, jumping ahead lets small jobs starve
  big ones forever. `report`'s blocked-idle figure (D41) shows what this
  costs.
- **D12 (user; precedence my call).** The class is resolved in this order:
  1. `--class`;
  2. `MUZZLE_CLASS` from the environment;
  3. the matched rule's `class`;
  4. the default: `normal` when `MU_MANAGED_AGENT=1`, else `high`.

  Workers, reviewers, fixers and refuters spawned by mu are `normal`. Humans
  and unmanaged agents are `high`. A mu-spawned orchestrator sets
  `MUZZLE_CLASS=high` in its launch command, so v1 needs no change in mu.
- **D13 (user).** Waiting has no limit by default. Every 30 s muzzle prints a
  progress line on stderr. `--timeout S` is opt-in and exits 75
  (`EX_TEMPFAIL`). *(Changed 2026-10-29 from 3, because mu 4.2.0 reads exit 3
  from a host template as a hand-back and mule uses 3 for a missing master.)*

### Running

- **D14 (user; overwrite my call).** The job's weight sets its parallelism
  through `MUZZLE_SLOTS`, `CARGO_BUILD_JOBS`, `RUST_TEST_THREADS` and
  `MAKEFLAGS=-jN`. muzzle overwrites inherited values, so the claim decides.
  An assignment inside the command string still wins, because it runs after
  muzzle. Rollout removes the hand-set caps (checklist step 15).
- **D15 (user).** On Linux with a systemd user manager, the job runs inside
  `systemd-run --user --scope -p MemoryMax=<D9> -p CPUWeight=<∝N>`. Where
  that is missing (macOS, no user manager), there is no cap and
  `status`/`doctor` say `advisory`.
- **D16 (user, revised by B1).** A claim belongs to the **process group the
  job runs in**, and lasts until that group has no members other than the
  dead muzzle.
  - When muzzle is its group's leader (pid == pgid), which is the case when
    the pi extension, a hook or a plain shell runs it as the first command,
    the job runs **in muzzle's own group**. A harness that kills the group
    (pi sends SIGKILL to the whole group on Esc or timeout) then kills the
    job too, and the next waiter's prune frees the slots.
  - When muzzle is not the leader, for example in `foo; muzzle run …` inside
    an interactive shell, it starts the job in a new group, and the docs say
    that killing the caller may leave the job running.
    *(2026-10-30, fix-run-signals: the new group's pgid is written in the
    same locked write as the spawn, so no pruner sees the running job's
    holder without it.)*
    *(2026-10-30, fix-run-signals-2: muzzle never hands the terminal to
    the new group (`tcsetpgrp`). Lending it took the terminal from callers
    that share muzzle's group (a harness's `Popen`, a script that reads
    while muzzle runs in the background), gave it back to a dead caller's
    group so the interactive shell exited, and sent Ctrl-C and Ctrl-Z to
    the job instead of the caller. So the job runs in the terminal's
    background: Ctrl-C and Ctrl-Z reach the caller's group, and muzzle
    forwards what it catches, as before. The limit: a job that reads the
    terminal (SIGTTIN) or changes its settings (SIGTTOU) stops. muzzle
    sees the stop (`WUNTRACED`), prints one `muzzle:` line saying the job
    needs the terminal and to run muzzle as the first command, then ends
    it as D18 does (SIGTERM and SIGCONT to the group, SIGKILL after the
    grace) and exits 128 + the stop signal, the code a shell gives a job
    stopped that way. The run line says `killed: signal` and the slots are
    freed. Ending it is the one outcome that doesn't hold slots without
    end: the job can't go on without the terminal, and muzzle won't take
    it. A plain SIGSTOP is left alone, since whoever sent it can continue
    the job.)*
  - Background children, `(gate > log &)`, stay in the group, so their slots
    stay held until they exit.
  - **Keeper (user, C1).** `muzzle run` returns when its top command exits,
    with that command's status, so launching in the background and polling
    keeps working. If the group still has other members at that point,
    muzzle first forks a detached **keeper**: it has no stdio, calls
    `setsid` so pi's group kill doesn't reach it, and takes over the holder
    entry (pid and start time) under the lock. Because of the `setsid`, the
    keeper is no longer in the job's group; it waits until that group is
    empty, then releases the slots and writes the `runs.jsonl` line.
    - Linux: CPU and peak memory come from the scope, which includes
      backgrounded processes.
    - macOS: `cpu_s` and `mem_peak_mb` are `null` for backgrounded runs.
    - A SIGKILLed keeper is pruned like any dead holder.
  - Known limit, to be written in the docs: a job that calls `setsid` or
    daemonizes leaves the group and frees its slots early.
- **D16a (user, 2026-10-29, after smoke_linuxpc).** Container gates. A job
  started through `distrobox enter`, `podman exec` or `toolbox run` runs in
  the container's own cgroup (`libpod-<id>.scope/container`, owned by the
  container's subuid). muzzle's scope only holds the `podman exec` and
  `conmon` processes, and conmon starts the job in its own session.
  - **Admission still works:** slots, queue, classes and nesting.
  - **Enforcement does not:** MemoryMax, CPUWeight, and the run's CPU and
    memory figures don't reach the job.
  - **Cleanup on a kill does not:** a group kill frees muzzle but not the
    in-container job.
  v1 therefore:
  - detects a container entry in the wrapped command (`distrobox enter`,
    `podman exec`, `toolbox run`, `docker exec`) and records
    `enforced: false` with `enforced_reason: "container"` in runs.jsonl,
    `--report` and `status`. `doctor` names the limit, and `report` marks
    those rules' figures as not measured, so it suggests nothing from them;
  - on a group kill of a container gate, keeps the slots held until the
    job's scope has no processes left (conmon exits when the in-container
    process does), instead of freeing them as soon as muzzle dies. A
    leaked build then waits instead of overloading.
  Follow-up (not v1): read cpu and memory from the container's outer
  `libpod-<id>.scope`, which the user owns, when muzzle is its only holder
  (D16a-b).
- **D17 (user, extended by B2).** Nested claims start at once without
  claiming. A claim counts as nested when either:
  1. an ancestor process is a live holder's muzzle or belongs to a live
     holder's group (`/proc` on Linux, libproc on macOS); or
  2. `MUZZLE_HOLD=<ticket>:<pid>:<start time>` is set and names a holder
     that is still alive in the state file.

  muzzle sets `MUZZLE_HOLD` for its job. The token is needed because
  ancestry stops at the container boundary: inside `distrobox enter`, the
  chain is `bash → conmon → 1` (checked on linuxpc). The environment and
  `$HOME` do cross it. Because the token is checked against live state, a
  stale or leaked one does nothing.
- **D17a (my call, builder check 2).** One budget per state file. The
  first `muzzle run` writes `budget`, `cores` and `ram_per_slot` into
  `state.json`, and later runs use the stored values. A config `slots =`
  replaces the stored values on the next run. The stored values are cleared
  when the file has no holders or waiters and is more than an hour old.
  `doctor` warns when its own reading differs from the stored values. This
  matters because a container's `available_parallelism` and `/proc/meminfo`
  can disagree with the host while both share one `state.json`.
- **D17b (fact).** swayward agents type `distrobox enter …` themselves in
  their bash strings, and pi has no `commandPrefix` or `spawnHook` set on
  linuxpc. The wrap therefore happens on the host, and the job enters the
  container inside muzzle's claim. pi runs `bash -c '<wrapped>'`, and for a
  single simple command bash execs muzzle, so muzzle leads pi's group. The
  smoke run checks this; when it fails, D16's fallback applies.
- **D18 (user).** `--run-timeout S` starts counting when slots are granted.
  When it fires, the job's group gets SIGTERM and then, after 10 s, SIGKILL,
  and muzzle exits 124. Time spent waiting never counts against the job.
  *(2026-10-30, fix-run-signals: a nested run (D17) shares the outer
  claim's group, so its timeout signals the nested child and that child's
  descendants, found by ancestry and tracked by pid and start time through
  the grace. The outer group is never signalled. A value too large for a
  duration is a usage error, exit 2.)*
  *(2026-10-30, fix-run-signals-2: a descendant orphaned before the
  deadline (`(cmd &)`) reparents away from the nested child, and ancestry
  loses it. On Linux a nested run with `--run-timeout` makes muzzle a
  child subreaper, so such orphans reparent to muzzle and the timeout
  still reaches them; muzzle reaps them as they exit. macOS has no
  subreaper, so there the orphan escapes the nested timeout. It stays in
  the outer claim's group, so the outer claim and its timeout still cover
  it. Muzzle adopts rather than scanning from spawn, because a scan every
  `POLL` reads the whole process table for the run's whole length and
  still misses an orphan that forks and exits between two scans.)*
- **D19 (user).** A waiter killed by SIGTERM or SIGINT prints
  `muzzle: killed while queued (position P/Q, waited Ws). Put timeout inside
  the command: muzzle run -- timeout N …`. Its ticket is not held for it. A
  SIGKILLed waiter cannot print, and its ticket is pruned.

### How claims are applied

- **D20 (user).** Repos are never changed. `contrib/fast-gate` and CI stay
  clean for other contributors. Claims come from outside the repo.
- **D21 (user).** Rules live in `~/.config/muzzle/config.toml` on each host,
  with optional per-project overrides. A command that matches no rule runs
  without a claim.
  *(Amended by 0.2, `2026-10-30-muzzle-0.2-paths.md` P1–P6: the per-project
  overrides are `[path."<dir>"]` tables that cascade onto the global rules
  by repo, and the root file can `include` per-machine files. `[project]`
  tables are removed.)*
- **D22 (user).** The rewrite lives in the CLI: `muzzle wrap` and
  `muzzle hook <harness>` do the matching, quoting and timeout handling.
  Each harness integration is a few lines of glue.
  *(2026-10-30: a command that already runs muzzle, by any path, is never
  wrapped again; see §CLI `wrap`. The pi extension also registers once per
  process, however many copies load.)*
  *(Amended by 0.2 P2–P4, P8: `match`, `wrap` and `hook` resolve the rules
  for the command's cwd through the path cascade, and `match --json`
  reports `source` as `global` or `path`, with `path` and `slots_from`.)*
- **D23 (user).** v1 ships:
  - a pi extension;
  - tested hook snippets for Claude Code and Codex;
  - an untested example plugin for opencode;
  - wrapping by hand for everything else.

  Cursor's `beforeShellExecution` can only allow or deny, so there is no
  rewrite there.
- **D24 (user).** In pi, the extension moves the tool's `timeout` to
  `--run-timeout`, so waiting cannot trigger the agent's own timeout (the
  "doom loop" fix). Other harnesses' timeouts are configuration, which
  muzzle cannot remove. There, `muzzle hook` passes on any timeout the
  payload carries, and the skill says to raise the harness's bash timeout.
  muzzle does not copy leasehold's "refuse at half the tool timeout"; that
  only turns waiting into retry loops.
- **D25 (user).** No PATH shims in v1. They add work to every cargo call,
  nest badly, and catch interactive use. The skill mentions them as
  something a user can set up.
- **D26 (user).** In pi, each wrapped tool result gets one line,
  `muzzle: waited Ws for N slots, ran Rs`, and a `muzzle` custom session
  entry with the same numbers.

### Measurement and tuning

- **D27 (user).** Every admitted run appends one line to
  `$XDG_STATE_HOME/muzzle/runs.jsonl` (schema below), including the job's
  CPU seconds and peak memory. On Linux with a scope these come from
  `CPUUsageNSec` and `MemoryPeak`. Otherwise they come from `wait4`'s rusage
  for the child tree. Lines are pruned after 30 days.
  *(Replaced by 0.2 P11: nothing is pruned. `runs.jsonl` rotates each UTC
  month, and past 16 MB, into `runs-YYYY-MM.jsonl.gz` archives that are kept
  forever. `report` reads the archives too.)*
- **D27a (user; detection orchestrator's, 0.1.1).** Each run records the
  `repo` it ran in, so run data can be split per repo. 0.1.1 only records
  it; reports and per-repo config come later. `repo` is the canonical path
  of the repo's **main checkout**, so every git worktree and jj workspace of
  one repo records the same path, or `null` outside a repo. It is found by
  reading files, never by running git or jj:
  1. Walk up from the cwd to the first directory holding `.jj` or `.git`.
     The nearest one wins, so a git repo nested in a jj repo is its own repo.
  2. `.jj` present (it wins over a colocated `.git`): if `.jj/repo` is a
     directory, this is the main workspace. If it is a file
     (`jj workspace add`; jj 0.46 writes `../../main/.jj/repo`), it holds a
     path relative to `.jj`. Canonicalise it and take its parent's parent.
     The target must be a directory named `repo` inside one named `.jj`; an
     empty or whitespace-only pointer, or any other target, can't be
     followed (step 4).
  3. Otherwise `.git`: a directory means this is the main checkout. A file
     `gitdir: X` names the common dir: `X/commondir`, relative to X, in a
     worktree, else X itself (a separate-git-dir checkout, a submodule).
     When the canonical common dir is named `.git`, the repo is its parent.
     Otherwise (a bare repo, `--separate-git-dir`, `.git/modules/<x>`)
     there is no shared main checkout, and the repo is the canonical common
     dir itself, so all of that repo's worktrees agree and two bare repos in
     one directory stay apart.
  4. A pointer that can't be followed falls back to the checkout found in
     step 1.
  `repo` is an added field in `runs.jsonl`, `--report` and `status --json`
  holders. Older lines lack it, and readers treat that as `null`.
- **D28 (user).** Each run records the config hash, rule and slots it ran
  under, so two periods can be compared per rule and per setting
  (`report --compare`).
  *(Amended by 0.2 P7: the hash covers the merged config, root plus
  includes, with every path table, and only the fields each rule entry
  sets. Its version tag is 2, so every 0.2 hash differs from every 0.1
  hash.)*
- **D29 (user).** `muzzle report` shows per-rule usage, machine-level
  figures, and a **suggested slot count** that names its evidence. It never
  edits the config; the model or the user does.
- **D30 (user; threshold my call).** A rule gets a suggestion only after at
  least **5 clean runs** (exit 0, not killed). Before that, `report` prints
  `insufficient data (N runs)`. A memory need can only raise a suggestion,
  never lower it.
- **D30a (user, C2).** Two signals can raise a weight. Without them the
  claim sets the job counts and the memory cap, so measured use can't go
  past the weight and suggestions could only fall.
  - **Saturated:** cores used p50 ≥ 90% of the slots held. `report`
    suggests an **experiment** (`try 8 (saturated at 6)`), marked as untested.
    `report --compare` confirms it when the run time drops, or rejects it
    when it doesn't.
  - **OOM:** a run the scope killed at `MemoryMax` (scope result `oom-kill`)
    is recorded with `killed: "oom"`. It counts as evidence for more
    memory: the suggestion covers its peak plus 25%. OOM runs are counted
    separately and are never clean.
  - The hard `MemoryMax` stays (D9). A kill is a clear signal, and the job
    would have hurt the machine anyway.
- **D31 (user).** A benchmark in two tiers:
  1. replay a trace with synthetic CPU-burners, which is cheap, repeatable,
     and runs on macOS;
  2. replay it with the real gate commands on linuxpc.

  Both produce the same report (D35).
- **D32 (user).** Benchmarks are a release task, not a gate. Each release runs
  tier 1 and commits the result to `docs/bench/`. No threshold blocks a
  release; the verdict comes from the proof (D44).

### Visibility and docs

- **D33 (user).** v1 ships `status [--json]`, `doctor [--json]` and

- **D34 (user).** A skill ships in the npm package: `skills/muzzle/SKILL.md`

### Benchmark data and sensitivity

- **D35 (user).** The benchmark report records, for each run:
  - makespan and throughput (jobs per hour);
  - wait and run p50/p90;
    *(2026-10-30: `wait_s`/`run_s` cover every replayed call, and an
    unmatched-heavy call never queues, so its wait is 0. `matched_wait_s`
    and `matched_run_s` give the same figures over matched calls only;
    fields are added, not renamed.)*
  - the most slots held at once;
  - the interactive probe: `git status` p95 in a scratch repo, and how late a
    10 ms sleep wakes, at p99;
  - load average, and out-of-memory kills.

  The probe is also a standalone command, `muzzle bench probe`, which
  appends one JSON line per sample, so cron can sample it during the
  rollout week. *(my call, DAG refute.)*
- **D36 (user).** The importer, `bench/from-museum`, is a script in the
  muzzle repo that reads `museum-search calls --json`. muzzle itself has no
  museum dependency. A trace is a plain file in a documented format, so
  other sources can produce one too.
- **D37 (user).** Only linuxpc data. The importer reads only `linuxpc/`
  store paths and refuses any other host. The checker rejects any trace
  that names one.
- **D38 (user).** Traces keep only fields on an allowlist (schema below).
  No command text, paths, workstreams, task names, session files or rule
  patterns. Agents become `a1, a2, …` within each trace. The mapping from
  each row back to its command stays in a local sidecar,
  `~/.local/state/muzzle/bench/<trace>.private.jsonl`, which is never
  committed.
- **D39 (user).** Projects are renamed `p1, p2, …` by default.
  `--keep-project NAME` keeps a name the user has made public.
- **D40 (user).** Before any commit, `bench/check-trace` validates traces
  against the schema and rejects any string outside the label lists,
  anything path- or home-like, hostnames other than `linuxpc`, emails, and
  token-like strings (gitleaks-style patterns). It runs in muzzle's CI and
  as a pre-commit hook. The first batch of traces also gets one read-only
  refuter pass (`mu_delegate`) looking for identifying content the schema
  might still let through, such as timing or label patterns.

### Machine-level report figures

- **D41 (user).** `report` also shows:
  - **utilisation**: slot-seconds held ÷ budget-seconds;
  - **blocked-idle**: slot-seconds left free while someone waited;
  - the share of time the queue was non-empty;
  - **CPU efficiency**: CPU seconds used ÷ slot-seconds held.

  `tune.md` reads these first:
  - high blocked-idle means D11 or over-sized heads are wasting cores;
  - low efficiency means the weights are too big;
  - a saturated budget at low CPU means the reserve is too big.

### Proof

- **D42 (user).** The museum baseline uses only **measured** calls
  (`duration_source = durationMs`) and states how many calls that covers.
  Background launches are counted but their durations are not used, because
  the estimates time polling, not the job.
- **D43 (fact).** museum has measured durations only from **2026-10-17**.
  The overload days (5–10 October) are all estimated: swayward has 873
  measured gate-like calls in October against 18,759 estimated, and mu has
  4,097 measured from 10-17 to 10-28. So:
  - the measured baseline comes from 10-17 onwards (busy days: 10-21, and
    10-24 to 10-27);
  - an overload day such as 10-08 is usable as a **replay workload** (when
    calls start, their sizes, their mix) but not as a measured baseline.
    Foreground estimates are close to call-to-result times. The trace marks
    each row's source.
- **D44 (user).** An improvement is claimed only from all three:
  1. a replay of a real linuxpc day, without and with muzzle, tier 2;
  2. the rollout week's `runs.jsonl` against the measured museum baseline;
  3. the interactive probe alongside both.

  The write-up goes in `docs/eval/` with its method. The README gets a short
  "measured" section that links to it, as mule's README does.
- **D45 (fact).** Under muzzle, `runs.jsonl` records a backgrounded gate's
  real runtime, because the keeper holds the claim as long as the group
  (D16), with CPU figures on Linux. This
  removes the polling bias for the rollout week. The eval says so.

## Interface

### CLI

```sh
muzzle run    [--slots N] [--class high|normal] [--rule LABEL] [--run-timeout S]
              [--timeout S] [--report FILE] -- CMD [ARGS…]
muzzle match  [--json] [--cwd DIR] -- 'SHELL STRING'
muzzle wrap   --json [--cwd DIR] [--timeout S] -- 'SHELL STRING'
muzzle hook   claude|codex            # hook JSON on stdin, reply on stdout
muzzle status [--json]
muzzle doctor [--json]
muzzle report [--rule LABEL] [--since D] [--until D] [--compare A..B C..D | --by repo] [--json]
muzzle bench  run TRACE [--mode none|muzzle] [--tier synthetic|real] [--speed X] [--out DIR]
muzzle bench  probe [--samples N] [--interval S] [--out FILE]
```

- `run` executes `CMD ARGS…` directly (argv, not a shell).
- `match` prints `{"slots":6,"rule":"gate","class":null,"source":"global"}`,
  or `{"slots":null}` when nothing matches. `--cwd` selects the path tables
  that apply (0.2 P2). *(0.2 P8: `source` is `"global"` or `"path"`, with
  `"path"` and `"slots_from"` added.)*
- `wrap` returns `{"command":"muzzle run … -- bash -c '<quoted>'","rule":"gate","slots":6}`,
  or `{"command":null}` for no match. It leaves a command that already
  runs muzzle alone: one whose first command word, past assignments and
  wrappers such as `env`, has basename `muzzle` (`muzzle run …`,
  `/abs/bin/muzzle run …`, `./muzzle`, `env A=1 muzzle run …`). `match`
  and `hook` treat it as no match too (D22, amended 2026-10-30: the pi
  extension's rewrite starts with an absolute path, so a second loaded copy
  wrapped it again). `--timeout S` turns into `--run-timeout S`.
  Every integration uses it.
- `hook claude|codex` reads a `PreToolUse` payload. For `Bash` with a match,
  it prints `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","updatedInput":{…,"command":"<wrapped>"}}}`.
  Otherwise it prints `{}`.
  *(user, 2026-10-29: Codex rejects `updatedInput` without `allow`, so
  `hook codex` always sends it. Claude applies `updatedInput` without a
  decision, and `allow` skips its permission prompt for the whole wrapped
  string. Rules match anywhere in the string, so `cargo build && curl x|sh`
  matches. `hook claude` therefore sends `allow` only when the command is
  one simple command, so nothing unreviewed can ride along: no `;`, `&`,
  `&&`, `|`, `||`, newline, `$(…)`, backticks, `<(…)`/`>(…)` or subshell
  parens outside quotes. The lexer respects quotes (`cargo test -- 'a&&b'`
  is simple) and treats anything it can't classify as not simple.
  Otherwise the reply carries `updatedInput` with no `permissionDecision`,
  and Claude's normal permission evaluation runs on the wrapped string. The
  docs and `harnesses.md` must say this.)*
- `--rule` is a **label** (each rule has a `name`; see Config). It shows up
  in `status`, reports and `runs.jsonl`.
- `--report FILE` makes `run` write, on exit:
  `{"waited_s":…, "ran_s":…, "slots":N, "class":…, "rule":…, "exit":…, "enforced":bool}`.
  Added later (fields are only added): `"kept"`, and `"admitted_ms"` /
  `"released_ms"`, epoch ms read under the state lock (null when nested,
  `released_ms` null when a keeper releases), so `bench run` counts slots
  held without overlap (bench_held_rounding), and `"repo"` (D27a), null
  outside a repo.

### Exit codes

| Code | Meaning |
|---|---|
| the command's own | passed through |
| 128 + signo | the command was killed by a signal |
| 124 | `--run-timeout` fired |
| 75 | `--timeout` fired while queued (`EX_TEMPFAIL`; not 3, which mu and mule reserve for a human hand-back) |
| 2 | bad usage or config |
| 125 | muzzle itself failed |

*(2026-10-30, fix-run-release: once the command has ended, its code
stands. A muzzle failure after that (a `--report` that can't be written, a
`runs.jsonl` line that can't be appended, a `state.json` save at release, a
keeper handoff that can't pipe or fork) is said on stderr and the exit is
still the command's. A failure while it runs (supervising it) is 125. A harness
that finds no report falls back as for a killed run. After spawn, no error
frees the holder entry: the job or a keeper may still hold it (D16), and
a waiter prunes it once the muzzle and its group are gone. The run line is
appended after `state.json` is saved, so it is written at most once.)*

### stderr lines

- Every 30 s while queued:
  `muzzle: queued 3/5, 14/14 slots held (a worker-7 gate 6, orch cargo-test 2, …)`
- Once when admitted after waiting: `muzzle: admitted after 312s (6 slots)`.
- On exit, when `--report` is unset: `muzzle: waited 312s for 6 slots, ran 241s`.
- The killed-while-queued message (D19).

### Config: `~/.config/muzzle/config.toml`

*(Amended by 0.2, `2026-10-30-muzzle-0.2-paths.md`. That spec defines path
tables, the cascade, includes and the hash; this section only summarises.)*

```toml
reserve = 2            # budget = logical cores − reserve
# slots = 12           # explicit budget; overrides reserve
include = ["machine.toml"]   # merged after this file; a missing one is skipped

[[rule]]
name  = "gate"
match = 'contrib/(fast-)?gate'
slots = 6
[[rule]]
name  = "cargo-test"
match = '\bcargo (test|nextest|clippy|build)\b'
slots = 2
[[rule]]
name  = "js-test"
match = '\b(vitest|npm (run )?test)\b'
slots = 2

[path."~/hacking/swayward-wm"]
[[path."~/hacking/swayward-wm".rule]]
name  = "cargo-test"
slots = 4              # reweight only; match is inherited
[[path."~/hacking/swayward-wm".rule]]
name  = "oracle-sweep"
match = 'oracle-sweep'
slots = 999            # capped to the budget (D8)
# class = "high"
```

- `name` is required, and unique within one file's global list and within
  one table. It is the stable label used in logs and reports, so a regex
  can change without breaking history.
- Path keys are directories. A table applies when its key is the command's
  target (the repo of its cwd, else the cwd) or an ancestor of it. Tables
  apply from the outermost to the nearest: an entry naming a rule in effect
  replaces only the fields it sets, and a new name is a new rule, tried
  before inherited ones. `enabled = false` turns a rule off below that key.
- Includes are relative to the root file. They may set `reserve`, `slots`,
  global rules and path tables, but not `include`.
- Patterns use the `regex` crate and are matched against the whole shell
  string, with no shell parsing. This is a heuristic.
- A missing file gets a commented template, as mule does, and muzzle
  continues with its rules.
- Unknown keys are errors (exit 2), naming the key. `[project]` is unknown
  since 0.2.
- The config hash (D28) is a short hash of the merged config (0.2 P7).

### `runs.jsonl` (one line per admitted run)

```json
{"v":1,"end":"2026-11-03T10:12:44Z","rule":"gate","slots":6,"class":"normal",
 "cfg":"a1b2c3","agent":"worker-7","cwd":"…","repo":"…","waited_s":312.4,"ran_s":241.0,
 "exit":0,"killed":null,"cpu_s":1490.2,"mem_peak_mb":9120,"enforced":true,
 "nested":false,"kept":false,"budget":14,"load1":9.8,"held":8}
```

`load1` and `held` (0.2 P12) are the 1-minute load average and the slots
held by others at admission. Older lines lack them.

`killed` is one of `null`, `"timeout"` (D18), `"oom"` (D30a), `"signal"`
(the caller killed the group), or `"holder"` (the muzzle or keeper was
killed and a waiter pruned the entry; no CPU figures).

Nested runs are not logged; their CPU is counted in the outer run. Runs that
match no rule are not logged, since unclaimed commands never reach muzzle.
`runs.jsonl` is local machine state and is never published. Traces are made
from museum, not from `runs.jsonl`.

### `report`

Machine section, for the period (D41):

- utilisation;
- blocked-idle slot-seconds;
- share of time the queue was non-empty;
- CPU efficiency;
- runs, total waited and total ran.
- unclaimed load p50/p90 (0.2 P12), from at least 20 runs.

`--by repo` (0.2 P9) gives rows per (rule, repo), each with the slots the
current config gives that repo and where they come from.

Per-rule rows:

| rule | runs | slots | wait p50/p90 | run p50/p90 | cores used p50/p90 | mem peak p90 | suggest |
|---|---|---|---|---|---|---|---|
| gate | 23 | 6 | 40/310 s | 220/290 s | 2.1/2.4 | 7.9 GB | **3** (p90 cores 2.4 over 23 runs) |
| cargo-test | 3 | 2 | … | … | … | … | insufficient data (3 runs) |

- Cores used = `cpu_s / ran_s`.
- The suggestion is `max(ceil(p90 cores), ceil(p90 mem / mem-per-slot))`,
  capped at the budget, from clean runs only (D30). *(my call: with D9,
  memory can only raise the count, which is what "memory can only raise"
  means here.)*
- Raising follows D30a. A saturated rule gets `try N+2 (saturated at N)`,
  capped at the budget, and a rule with OOM runs gets
  `ceil(1.25 × max oom peak / mem-per-slot)`. Each suggestion is tagged
  `measured`, `experiment` or `oom`.
- `--compare A..B C..D` prints the same rows for both periods side by side,
  with deltas, split by config hash when it changed inside a period.

`report` also lists the top heavy commands that match no rule. It can't see
those itself, so it prints the command to find them
(`museum-search calls --min-secs 30 --tool bash`) rather than guessing.

### Benchmark runner

`muzzle bench run TRACE` replays the calls at their offsets. `--speed X`
compresses time; the default is 1. Each call runs as:

- **synthetic** (tier 1): a CPU burner sized to the call's rule, burning
  its threads for `dur_s`. In `--mode muzzle` the threads are the claim
  (the rule's slots). In `--mode none` they are the rule's slots capped at
  the role cap, because the trace's `dur_s` was measured under those caps.
  Either way, an uncontended call takes about `dur_s`, and only contention
  stretches it. `light` calls are skipped, and `unmatched-heavy` calls burn
  one thread (an explicit `--threads 1`, never the inherited
  `CARGO_BUILD_JOBS`).
- **real** (tier 2): the command for each rule label, taken from a local
  mapping file (`bench/real.toml`, not committed), such as
  `gate = "cd ~/hacking/swayward-wm/swayward && git checkout -q <pinned> && contrib/fast-gate"`.

`--mode none` is **today's practice** (C3): every call starts straight
away with the role caps from the briefs (`CARGO_BUILD_JOBS` 4 for workers,
6 for the orchestrator, 2 for reviewers and other roles), and no queue.
`--mode muzzle` runs each call through `muzzle run` with a private state
directory and the rollout config, with no role caps.

`--window busiest:3h` replays the busiest 3-hour window of the trace, the
one with the most matched call-seconds. A window replays the calls that
start inside it, whole, and is scored the same way, so a call that started
before the window counts towards neither. For tier 2, each replayed agent
(`a1`, `a2`, …) gets **its own worktree and target directory**
(`CARGO_TARGET_DIR=<workdir>/<agent>/target`, overriding any inherited
value, for setup and replay alike), created at
the pinned commit and built once before either mode runs, so both start
with the same cache. *(my call: the pre-build leaves both modes equally
warm, and cache state isn't what's being measured.)* While running, the
probe from D35 runs too. Output goes to `--out DIR`:

- `result.json`: the D35 figures;
- `runs.jsonl` (in muzzle mode);
- `summary.md`.

*(my call: synthetic burners take their thread count from the rule's slots
because the trace has no CPU data from museum. Tier 2 is where real CPU
shows up.)*

## Architecture

Six units, each with one job.

1. **`admit`**: a pure function `(state, now, liveness) → (pruned state,
   admitted tickets)`. It holds all the queue rules (D8, D10, D11) and does
   no I/O.
2. **`state`**: reads and writes `$XDG_STATE_HOME/muzzle/state.json`
   (default `~/.local/state/muzzle/`) while holding an exclusive lock on
   `state.lock` (`std::fs::File::lock`). Every change is a short
   read-modify-write under the lock.
   - Waiters: ticket, pid, start time, slots, class, agent, rule, cwd.
   - Holders: ticket, muzzle pid and start time, pgid, slots, class, agent,
     rule, cwd, run start.
   - A monotonic `next_ticket`.
3. **`proc`**: the platform layer.
   - Liveness: pid plus start time, so a recycled pid counts as dead.
   - The members of a group: a `/proc` scan, or `proc_listpgrppids`.
   - Ancestry.
   - Cores and RAM.
   - Rusage.
   - Whether systemd is reachable, and the scope's figures.
4. **`run`**: the orchestration.
   1. Check for nesting (D17).
   2. Enqueue, then poll every 250 ms; each poll runs `admit` under the
      lock.
   3. Once admitted, spawn the command in muzzle's group or a new one (D16),
      inside a systemd scope when possible, with the env from D14 and
      `MUZZLE_HOLD`.
   4. Forward catchable signals to the group. One exception: when muzzle
      leads the group (D16), it drops SIGINT and SIGQUIT instead of
      forwarding them. A terminal sends those to the whole group already,
      and a second SIGINT means "force quit" to cargo and friends. A
      `kill -INT` aimed at muzzle's pid alone is therefore dropped too;
      signal the group (`kill -INT -<pgid>`) or send SIGTERM.
      *(Amended 2026-10-30: documents the existing `src/run/spawn.rs`
      behaviour, found in review.)* *(2026-10-30, fix-run-signals: a signal
      the caller set to `SIG_IGN`, such as `nohup` or `trap '' HUP`, is
      neither caught nor forwarded. The job inherits the ignore through
      exec.)*
   5. Wait for the command. If the group is empty apart from muzzle,
      release the slots and append to `runs.jsonl`. Otherwise hand off to a
      keeper (D16).
   6. Write `--report` (with `"kept": true` when a keeper took over) and
      exit with the command's status.
5. **`rules`**: config loading, `match`, `wrap`, `hook` formats, and the
   config hash.
6. **`report` and `bench`**: these read `runs.jsonl` or replay a trace. They
   don't touch admission except through `muzzle run`.

Pruning, inside `admit`:

- A waiter whose pid plus start time is dead is dropped.
- A holder is dropped once its group has no live members other than its
  muzzle, and that muzzle is dead.
- A holder whose muzzle was SIGKILLed while its group still has members keeps
  its slots until the group empties. Such a run gets a `runs.jsonl` line
  from the waiter that prunes it, with `killed: "holder"` and no CPU figures.
  Its `end` and `ran_s` stop at the holder's `seen_ms`: the last time an
  `admit` pass kept it or its muzzle or keeper beat (every 2 s), not the
  prune (ran_s_lag_followup).

The queue must keep working with no muzzle process alive between
invocations, which is why every live waiter re-runs the pruning.

### Systemd scope on Linux

With the scope, muzzle starts `systemd-run --user --scope --quiet -p
MemoryMax=… -p CPUWeight=… -- CMD…`, and the job stays in muzzle's group or
the new one. At startup muzzle probes once whether the user manager can be
reached (`systemctl --user is-system-running`, or its D-Bus equivalent) and
caches the result for the run. When it cannot be reached, the job runs
directly and is marked advisory. Afterwards, the scope's `CPUUsageNSec` and
`MemoryPeak` are read before the scope goes away. Inside a container where the
user manager can't be reached, runs are advisory. The pi extension wraps the
whole bash string on the host side of `distrobox enter`, so swayward gates
are still enforced there.

### Prior art reused

- From mule `src/lock.rs`: recording PIDs at claim time and skipping a dead
  waiter's ticket, written up as a reproduced wedge. The queue itself is new,
  because mule's lock has a single holder and this one has weighted shares.
- From leasehold: `doctor`'s enforced/advisory line, `CPUWeight` scaled to
  the claim, busy messages written so the model can act on them, and the
  interactive probe in its benchmark.

## Integrations

### pi extension

Ships in the same npm package as the binary (`@mu-crew/muzzle`, with mule's
per-platform optional dependencies, and the `pi-package` keyword).
`npm i -g @mu-crew/muzzle` puts `muzzle` on PATH, and
`pi install npm:@mu-crew/muzzle` loads the extension and the skill. The

- `tool_call` on `bash`: run `muzzle wrap --json --cwd <cwd> [--timeout T]
  -- <command>`. When the reply's `command` is not null, set `input.command`
  to it, add `--report <tmpdir>/<toolCallId>.json`, and delete
  `input.timeout` (D24).

### Claude Code and Codex

*(Decided 2026-10-29, human, after review_skill_docs:)* `hook claude`

## The skill

`skills/muzzle/` ships in the npm package and loads with `pi install`. Other
harnesses read it as markdown (a Claude Code skills folder, or a pointer in
`AGENTS.md`).

- **`SKILL.md`**: what muzzle is, and how to read its lines (queued,

  4. Check the change with a tier-1 replay of a recent trace, against the

  5. Keep the change, then after a few days check
     `report --compare <before> <after>`.
  6. Write one line in the config next to the edited rule saying why.
- **`recipes/bench.md`**: make a trace with `bench/from-museum` (linuxpc

## Out of scope for v1

- Placement across hosts (B): the next spec.
- tmux options and murmur or tsesh display.
- "Usually takes ~Xm" lines in the queue messages. The data exists in
  `runs.jsonl`; showing it can wait.
- Memory polling and kills on macOS.
- A GNU make jobserver per claim (the `jobserver` crate can add it later).
- More than two classes, and fair turns per session.
- Holding a place for a killed waiter.
- Tracking jobs that call `setsid` and leave their group.
- Load-aware admission.
- SQLite for state, the run log or traces (user-agreed 2026-10-29: plain
  JSON/JSONL). The data is small and always read in full scans, so an index
  buys nothing. JSON with a version probe fails cleanly when host and
  container binaries differ; SQLite's WAL needs shared memory across that
  boundary. Traces must stay readable diffs in a public repo, and no C
  build is added. Revisit if mu host integration needs joins across hosts'
  logs, if retention grows past ~100k lines, or if readers need concurrency
  while a write is in progress. A cheaper step first: monthly
  `runs-YYYY-MM.jsonl` files, if the daily prune ever shows up in waits.
- PATH shims, Cursor rewriting, and a tested opencode plugin.
- muzzle editing its own config.

## Prior art

- **leasehold** (github.com/chalkworth/leasehold). Python, ~38k lines,
  alpha, started 2026-10-15. Nearly the same admission model: slots per CPU,
  a reserve, weighted leases, env sizing, systemd scopes, PATH shims and a
  Claude Code hook. Not adopted because:
  - it needs a daemon (HTTP API, SQLite ledger, 15 s lease renewals), which
    STANCE rules out;
  - it is Linux-first;
  - its turns are fair per session, where we want the orchestrator first;
  - it refuses at half the tool timeout;
  - it has no pi integration.

  Its benchmark (8 CPU, 16 GiB): `git status` p95 went from 981 ms to 103 ms,
  and the same work took 1.5× as long.
- **GNU `sem`, waitlock**: counting semaphores, one slot per holder, no
  weights or classes. `sem` is the stopgap.
- **nq, task-spooler, pueue**: job queues that own the job and its output;
  tsp and pueue run daemons.
- **mbx (jdx/mr-boxington)**: a machine-wide permit pool for each rustc,
  weighted by measured memory. Cargo only, and complementary. Its "weight
  from measured use" idea is the same as `report`'s suggestions, at a finer
  grain.
- **steve, guildmaster**: a CUSE jobserver for the whole machine. Only
  jobserver-aware tools can use it, and their writeups show cargo holding
  tokens and token loss on crash.
- Harness hooks: Claude Code `PreToolUse` `updatedInput`
  (code.claude.com/docs/en/agent-sdk/hooks); Codex `PreToolUse`
  (aftergradient.com/guides/codex-hooks, a third-party guide, to be checked
  against Codex's own docs at build time); opencode `tool.execute.before`
  (opencode.ai/docs/plugins); Cursor `beforeShellExecution`, allow/deny only
  (cursor.com/docs/hooks).

## Next: mu host integration

The follow-up spec, after v1 has run for a while. This section records the
user's intent; it is not a design.

> after muzzle v1 is done, mu host gets integrated so the orchestrator can
> schedule work better.

What v1 provides for it:

- `muzzle status --json`, a quick read-only call that a mu host profile's
  `exec` template, or mule, can run on each host. It returns budget, free
  slots, the queue and enforcement. Its fields are stable and only ever
  added to.
- `runs.jsonl` and `report --json` on each host. These give how long a rule
  takes there and how many cores it really uses, so placement can use
  measured costs rather than slot guesses.

Facts that landed after v1's design (mu 4.2.0, mule 0.3.0, 2026-10-29):

- mu remote workers can use the **lease transport**: the pane runs
  `mule run --lease`, and no ssh session is held for the agent's life
  (mu `docs/specs/2026-10-28-lease-transport.md`). A lease pane holds no
  `host_channels` row, so `--max-sessions` now counts only short operations.
  That makes muzzle's slots the remaining capacity signal for remote
  workers.
- The status call is `mule exec --host <h> -- muzzle status --json`. That is
  one short locked call, with no new transport in mu.
- Exit 3 from any mu host template is a hand-back (`HostHandbackError`).
  muzzle never exits 3 for its own reasons (queue timeout is 75), so a remote
  `muzzle run` cannot be mistaken for "human needed".

Questions that spec will need to answer, not answered here:

- Does mu read host capacity on demand (at spawn or `mu next`) or show it in
  `mu host list`?
- What does it place: workers, command gates, or both?
- Does it combine `max_sessions` (ssh channels) with muzzle slots?
- Does remote work go through `mule run` with `muzzle run` as the remote
  command?
- Should a mu role variable replace `MUZZLE_CLASS`?

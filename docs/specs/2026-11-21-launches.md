# muzzle: process launches per run

Status: requested by the human (2026-11-21 brief), implemented and
reviewed by a five-angle panel whose findings were refuted one by one. It
adds a field to `runs.jsonl` and a column and a JSON field to `report`,
all add-only (AGENTS.md invariants). This spec wins where it and the v1
spec disagree.

## Problem

On some hosts a process launch costs far more than on others: around
100 ms instead of about 1 ms. Much of that cost lands on other processes,
not on the job. `cores` (`cpu_s /
ran_s`) then calls a job that starts hundreds of processes light, CPU
efficiency reads low, and the tune loop keeps the job's weight low while
the machine is saturated. muzzle has no figure for how many processes a
job starts.

## Decisions

**L1 `procs` in `runs.jsonl`.** The number of processes seen in the job's
process group, sampled while the job runs, its `--run-timeout` grace
included (that time is in `ran_s` too). A process is told apart by its
pid and start stamp, so one that leaves the group and comes back counts
once and a recycled pid counts again. The start stamp is read only for a
pid that wasn't in the previous sample. The top command is counted even
if it exits before the first sample, so `procs >= 1`.

- It is a lower bound. A process that starts and exits between two
  samples is missed, and so is one that leaves the group for good
  (`setsid`, as for claims, D16). Measured on a Mac where a launch took
  ~100 ms: 50 × `/usr/bin/true` in 1.5 s counted 21 of 51; 50 × `sh -c
  true` (6.4 s) counted 44 of 51; 30 × `sleep 0.05` counted 31 of 31.
  Where launches are slow, processes live past a sample and the count is
  close; where they are cheap it undercounts, and there it matters less.
- macOS samples every `TICK` (20 ms): a listing is one
  `proc_listpids(PROC_PGRP_ONLY)` plus a stat per member, 19 µs with 21
  members on a 1180-process host (release build), about 0.1% of a core per
  running job. Linux samples every `POLL` (250 ms), because a group listing
  there reads all of /proc: the cost D18's 2026-10-30 note weighed against
  adoption (a scan every `POLL` for the run's whole length). Linux's cost
  is not measured yet.
- A keeper (D16) goes on counting from its own group listing, every
  `POLL`, so a backgrounded job's short-lived processes are undercounted
  more than a foreground job's.
- A container run (D16a) is not sampled and its line has no `procs` key:
  the container's processes aren't in the group. (`cpu_s` is written as
  `null` there; `procs` is left out, like every unmeasured `procs`.) Older
  lines and lines a pruning waiter writes (`killed: "holder"`) have no
  `procs` either. Nested runs aren't logged (D17); their processes count
  in the outer claim's group.

**L2 `report` shows `procs/s p50/p90`** after `cores p50/p90`, as
`procs / ran_s` over the clean runs that carry `procs`. `--json` adds
`procs_per_s: {p50, p90}` per rule, null when no clean run has a count.
`--by repo` has the same column. `--compare` doesn't show it.

**L3 Suggestions don't use launches yet.** A launch's cost is outside the
job and differs by about 100× between hosts, and muzzle has no per-host
figure to turn launches into cores. A weight raised by a guess would be
the old over-sized heads again (D30, D41). Until there is one, `procs/s`
is read by hand (L4).

**L4 Tuning by hand.** `recipes/tune.md`: `procs/s` is a hint, not proof.
On a host where launches are slow and the machine is sluggish while CPU
efficiency reads low, a rule with high `procs/s` and low `cores` may be
held up by launches its `cores` doesn't show. Confirm before acting (the
run gets faster when fewer such jobs run at once). The answers there are a
smaller budget (`overcommit = 1.0` and a larger `reserve`, which leaves
cores for the work a launch causes elsewhere) and weights for those rules
above their `cores` p90.

## Open

- A launch-latency probe (`bench probe` timing a `posix_spawn` of
  `/usr/bin/true`) as the per-host cost L3 lacks. A candidate suggestion is
  `ceil(cores p90 + procs/s p90 × launch_s)`, which treats each launch as
  `launch_s` of a core held. That is wrong where that work runs in
  parallel and right where it serialises; it needs measuring against
  `git status` p95 under load before it goes into `report`.
- Linux sampling cost, and whether an enforced run should read the scope's
  `cgroup.procs` instead of scanning /proc.

# muzzle 0.2.0: path cascade, includes, report by repo

Status: approved by the human (brainstorm 2026-10-30, Q1–Q9 "yes to all").
It amends the v1 spec (`2026-10-29-muzzle.md`) at D21, D22, D28 and §Config.
Where this spec and the v1 spec disagree, this one wins.

## Problem

Rule weights in 0.1 are global. The baseline shows that one rule behaves very
differently per repo: `cargo-test` has p50 from under 1 s (vtmux) to 32 s
(swaywardlock), and p90 from 28 s to 136 s. 0.1's `[project."<glob>"]` tables
were meant for this but go unused, for two reasons:

- They match the cwd, so mu worktrees (under `~/.local/state/mu-next/worktrees`)
  miss them.
- Rule names are unique across the file, so a project table can't reweight a
  global rule. It can only add new ones.

The human also wants one config tracked in dotfiles that pulls in an untracked,
per-machine file.

## Decisions

The human said "yes" to Q1–Q9, with one instruction: **no backwards
compatibility and no migration paths**, because nobody else uses muzzle. That
instruction supersedes Q1's deprecation and Q7's hash continuity, as noted in
P1 and P7.

**P1 Path tables replace project tables.** `[path."<dir>"]` with
`[[path."<dir>".rule]]` entries. Keys are directories, not globs: `~` is
expanded, and the path is canonicalised when it exists (otherwise it is
normalised lexically). `[project]` is removed, so it is an unknown key and
exits 2, like any other unknown key. *(Q1, with the human's no-compat override:
no alias, no warning.)*

**P2 What a table matches.** The **target** of a command is the repo of its cwd
(`repo::repo_of`, the main checkout, as recorded since 0.1.1). If the cwd is in
no repo, the target is the canonical cwd. A table applies when its key equals
the target or is an ancestor of it, compared by whole path components, so
`~/hacking/crew` doesn't match `~/hacking/crewmate`. Every worktree of a repo
therefore gets the same chain. A table can't target a subdirectory inside a
repo. *(Q2)*

**P3 Cascade and merge.** The effective rules for a target start from the
global `[[rule]]` list. The applicable tables are applied from the outermost
(shortest key) to the nearest. Inside a table, each rule entry is handled by
`name`:

- **The name is already in effect:** merge field by field. Any of `match`,
  `slots`, `class` and `enabled` that the entry sets replaces the inherited
  value. Fields it leaves out are inherited.
- **A new name:** a new rule. It must set `match`. `slots` defaults to 1, as
  in 0.1.
- `enabled = false` takes the rule out of matching for that subtree. A deeper
  table can set `enabled = true` again. A global rule may set
  `enabled = false`, which lets an included machine file turn on a rule that
  the root file ships disabled.

Names are unique within one table, and within the global list of one file. The
same name in different tables is the point of the cascade. *(Q3)*

**P4 Rule order.** First match wins, as in 0.1. Merging an inherited rule
keeps its position. A table's new rules go in front of everything inherited,
in the table's file order, so the nearest table's new rules are tried first.
*(Q4)*

**P5 Includes.** The root file may set `include = ["<path>", …]`. Paths are
relative to the root file's directory, with `~` expanded. Rules for includes:

- A missing file is skipped silently, and `doctor` lists it as `not found`.
- Any other read error, or a parse or validation error, exits 2 and names the
  file.
- An included file can't set `include` (exit 2): there is one level only.
- Includes are applied after the root, in list order. Each one is a layer with
  the same shape as the root, merged into it:
  - `reserve` and `slots` replace the root's values;
  - global rules merge by name (P3 merge), and new names are **appended** to
    the global list;
  - path tables with the same key merge by rule name, and new keys are added.
- No `config.d/` directory.

*(Q5, Q6)*

**P6 Budget keys** (`reserve`, `slots`) are allowed in the root and in includes
only, not in path tables. They describe the machine. *(Q6)*

**P7 Config hash (D28).** It is computed from the effective, merged config:

- `reserve`, `slots`, the global rules, and every path table's entries, sorted
  by canonical key;
- each rule entry with only the fields it sets, including `enabled`.

It does **not** depend on a particular target. A missing include doesn't
contribute anything. The version tag `v` becomes 2, so every 0.2 hash differs
from every 0.1 hash. *(Q7 superseded by the human's no-compat instruction:
continuity is dropped and the hash changes once on upgrade.)*

**P8 Provenance.** Each effective rule records where each of its `match` and
`slots` values came from: an **origin**, which is a file plus an optional
table key (`None` means the file's global list).

- `match --json` replaces `"source": "global"|"project"` and `"project"` with
  `"source": "global"|"path"`, plus `"path": "<key>"` (the nearest table that
  touched the rule) and `"slots_from": {"file": "…", "path": "<key>"|null}`.
- `doctor` lists the files: root plus each include, with `found` or
  `not found`, and the number of path tables.

**P9 `report --by repo`.** Groups by (rule, repo). A null repo shows as
`(none)`. The 5-clean-run minimum and the suggestion logic are unchanged. For
each row's suggestion, the config is resolved for that repo, and the
suggestion names where the current `slots` comes from, for example
`now 3 (from [path."~/hacking/crew"] in machine.toml)`. Without `--by`, the
report is unchanged (rows per rule). `--by repo` with `--compare` exits 2:
that combination is out of scope. *(Q8)*

**P10 Version 0.2.0, breaking.** There are no deprecations and no migration
code. The CHANGELOG says what breaks: `[project]` tables, `match --json`
`source`/`project`, and the config hash. *(Q9, with the no-compat override.)*

## Builder-check answers (orchestrator's calls, 2026-10-30)

The builder check raised six questions. None changes what the human
approved, so each one is settled here as the orchestrator's call.

**B1 Key identity.** A table's identity is its canonical path (P1).
- Two keys in **one file** that canonicalise to the same path exit 2, and
  the message names both spellings.
- The same canonical key in the root and an include is the same table, and
  the include merges into it (P5).
- Displays (`match --json` `path`, `slots_from.path`, report lines) use the
  key as written in the **first** file that defines the table.
- P7 sorts by canonical path.

**B2 Validation at load.** After merging, an entry with no `match` must
name a rule that is already in effect where it applies:
- for an include's global entry, a rule in the global list before that
  include (root or earlier includes);
- for a path-table entry, a rule in the merged global list or in an
  ancestor table, meaning a key that is a strict component prefix of this
  key.

Otherwise it exits 2 and names the entry. This makes `resolve(cwd)`
infallible.

**B3 `run --rule NAME` and replay.**
- `run` takes the rule as resolved at its cwd. When the rule isn't active
  there (disabled, or defined only in a table that doesn't apply), it falls
  back to the first definition in file order (global list, then tables by
  canonical key) for `class`. This matches v1, where a `--rule` from a
  pre-wrapped command is trusted.
- The warning `rule X is not in the config` stays for names that are
  nowhere in the config.
- `bench/replay` looks up slots by name the same way, so a trace that names
  a table-only or disabled rule keeps working.
- `Config::rule_anywhere(name)` is the shared lookup.

**B4 `source`.** `"path"` when any applicable table touched the rule
(reweight-only counts). `path` is the nearest such table. `slots_from` says
where `slots` came from.

**B5 Read errors.** An include that exists but can't be read is
`ConfigError::Read`, with the same exit as the root today (internal).
Parse and validation errors in any file exit 2. A NotFound include is
skipped (P5).

**B6 `report --by repo` "now N".**
- **N** is the **current** config resolved for that repo (its canonical
  path as the target). The `(none)` row resolves the global list only.
- When the slots in the row's runs differ from N, the line shows both:
  `now 2 (from [path."~/hacking/crew"] in config.toml); runs used 4`.
- When the rule isn't active at that repo now, the line says
  `not in the current config here`, and there's no suggestion.
- Suggestions are computed from the run history, as in 0.1, and compared
  with N.

**Hash detail.** "Only the fields it sets" is intended: writing
`slots = 1` out explicitly changes the hash, because in a table it overrides
an inherited value. v1's test that a written-out default is stable is
rewritten.

**P11 runs.jsonl: monthly gzip archives instead of the 30-day prune**
(human, 2026-10-30: "add .zstd or .gz to logrotate, keep a lot of history
for free; doctor can warn if it's big"). This replaces D27's 30-day prune.
- **Rotation.** On append, still under the state lock: when the first line
  of `runs.jsonl` is from an earlier UTC month than now, its lines are
  gzipped into `runs-YYYY-MM.jsonl.gz` (the month of the first line), and
  `runs.jsonl` starts again.
  - The write goes to a temp file, then fsync, then rename. Only then is
    `runs.jsonl` truncated, so a crash leaves at worst one month in both
    files. `report` drops exact duplicate lines, so that case is harmless.
  - If the archive name already exists, which happens after a crash or a
    clock jump, the new archive gets the suffix `-2`, `-3` and so on.
  - A busy month can't grow the live file without bound: when `runs.jsonl`
    passes 16 MB it rotates the same way into the next free suffix.
- **Format: gzip, not zstd** (orchestrator's call). Built with the pure-Rust
  `flate2` (miniz_oxide), which builds cleanly for musl and macOS. `zcat` and
  `jq` work on every machine. zstd -19 is ~20% smaller on linuxpc's log
  (7.5 KB versus 9.1 KB for 160 KB raw: about 17× for gzip), and it needs a C
  library.
- **Retention.** Archives are kept forever. At linuxpc's rate that's about
  2–5 MB of gzip a year.
- **report** reads the archives whose month overlaps the period plus
  `runs.jsonl`. The default period is unchanged: everything that's there,
  which is now more than 30 days. `--since`/`--until` let it skip archives
  outside the period without opening them.
- **doctor** shows the live file and the archives: count, total size,
  oldest month. It warns when the archives pass 256 MB or the live file
  passes 16 MB (meaning rotation is failing).
- **bench and replay** write their own `runs.jsonl` in their output
  directory, with no rotation. They are unaffected.

**P12 Unclaimed load** (human, 2026-10-30: "muzzle is opt in, we expect
users' agents to behave, but remove obvious gotchas"). Agents sometimes put
heavy work inside throwaway scripts (`./run.sh`, `python3 /tmp/x.py`, a
heredoc). muzzle can't see inside them. In the baseline, about 500 heavy
foreground calls (44 wall-hours) were scripts, and none of them matched a
rule. 0.2 measures the gap and documents it. It doesn't try to close it.
- **Record.** At admission, a run record gets `load1` (the 1-minute load
  average from `getloadavg`, on Linux and macOS) and `held` (the slots held
  by others at that moment, read from the state already loaded under the
  lock). Both are optional fields: older lines simply lack them. Nested
  runs and container runs record them too.
- **Report.** The machine section gets a line: `unclaimed load: p50 X,
  p90 Y cores`. Each value is `max(0, load1 − held)` over the period's
  runs that carry both fields. It is shown only when at least 20 runs
  carry them, and JSON has `unclaimed_load: {p50, p90, n}`. It's a rough
  signal: load average lags and counts I/O wait on Linux, and the docs say
  so.
- **Skill.** A rule in SKILL.md: a script you write that runs builds or
  tests is wrapped as a whole, with
  `muzzle run --rule <name> -- ./script.sh` (or `bash -c '…'`). Don't
  hide gates in a script to avoid the queue. tune.md gets a line on
  reading the unclaimed-load figure: when it is high, find the unmatched
  heavy commands and add rules, or raise the reserve.
- **Not doing:** PATH shims for `cargo`, `npm` and so on. The human:
  "too heavy-handed, we'll never do that". Recorded as parked
  `path_shims_never`.

**Onboarding (human, 2026-10-30).** No discovery mode. The agent writes
the config from the skill and runs trials. muzzle stays simple and
predictable and ships no slow default footguns.

## Call sites (caller's view)

Updated for 0.2.1 `command` rules (`2026-10-30-muzzle-0.2.1-command-rules.md`
C7); in 0.2.0 these were `match` regexes.

```toml
# ~/.config/muzzle/config.toml (tracked in dotfiles)
include = ["machine.toml"]

[[rule]]
name = "cargo-test"
command = ["cargo test", "cargo nextest", "cargo clippy", "cargo build"]
slots = 3

[[rule]]
name = "js-test"
command = ["vitest", "npm test", "npm run test*"]
slots = 2

[path."~/hacking/crew"]
[[path."~/hacking/crew".rule]]
name = "cargo-test"
slots = 2                       # reweight only; command inherited

[path."~/hacking/crew/murmur"]
[[path."~/hacking/crew/murmur".rule]]
name = "js-test"
enabled = false
```

```toml
# ~/.config/muzzle/machine.toml (untracked)
reserve = 2
[[rule]]
name = "cargo-test"
slots = 4                       # this machine's global weight
```

Result in `~/hacking/crew/mu` and every mu worktree of it: `cargo-test` has 2
slots (from `[path."~/hacking/crew"]` in config.toml). In
`~/hacking/swayward-wm/swayward` it has 4 (from machine.toml's global list).

```rust
// Code-facing shape (names are binding for the units below).
let cfg = Config::load()?;                    // root + includes, merged
let eff = cfg.resolve(cwd);                   // P2 target, P3/P4 cascade
let m: Option<Match> = eff.matches(command);  // first enabled match
cfg.hash();                                   // P7, target-independent
```

## Scope

**In:**
- path tables, the cascade and `enabled`;
- includes;
- the provenance fields in `match --json` and `doctor`;
- `report --by repo`;
- an updated template, `bench/linuxpc-config.toml`, SKILL.md, recipes, README
  and the v1 spec's amended lines;
- CHANGELOG and the version bump.

**Out:**
- repo-local `.muzzle.toml` (the human decided on a single central file;
  maybe later, as "the repo declares heavy commands, the machine decides
  slots");
- globs in path keys;
- tables for subdirectories inside a repo;
- `config.d/`;
- nested includes;
- `--by repo` together with `--compare`;
- any runs.jsonl schema change (provenance is resolved from the current config
  at report time).
